## What already agrees

- All **21 module IDs, parameter-ID sets and input/output-ID sets** in `public/wirescape_modules.json` match native manifests under `native/modules2/*/module.json` and `native/sdk/examples/*/module.json`. This compares identifiers, not DSP equivalence or every metadata value. Keep these IDs.
- **OPEN-9 has supporting implementation evidence:** both engines sum modulation in normalized knob space, clamp, apply taper and quantize. Native `Parameter::plain()` and `Engine::Impl` processing in [engine2.cpp](https://github.com/kalharbi11/wirescape/blob/6e3c253550428f2bb964af4434bd429b5284cce2/native/engine2/engine2.cpp#L70) agree with UI `FakeEngine` and `modules/registry.ts` for the current linear/log catalogue. Native also supports exponential taper, smoothing, per-voice offsets and audio-rate processing; the prototype does not establish equivalence for those. Retain normalized amounts and add cross-engine vectors for log cutoff, linear controls, negative amounts, multiple sources, bounds and stepped parameters.
- Native `engine2` supports multiple signal edges into one input and feedback sub-blocks. The UI can save multiple edges, although ordinary drop currently replaces and Shift-drop adds. **Recommended default:** use PLAN Q-B's sum behavior when integrating; do not silently discard saved edges. This is an interface behavior follow-up, not an engine-format decision.

## Concrete gaps to close before a real-engine claim

| Gap | Evidence and recommended treatment |
|---|---|
| Browser-generated v2 is incomplete for native execution | UI `PatchV2` requires only format/version/modules/connections; native [runtime_patch.cpp](https://github.com/kalharbi11/wirescape/blob/6e3c253550428f2bb964af4434bd429b5284cce2/native/document/runtime_patch.cpp#L30) requires a `settings` object, each module's positive `version`, and nonempty `outputs` with explicit output port and `bus_channel`. Native [patch_document.cpp](https://github.com/kalharbi11/wirescape/blob/6e3c253550428f2bb964af4434bd429b5284cce2/native/document/patch_document.cpp#L86) also validates these shapes. Imported Qt starters preserve that metadata, but adding/deleting modules can leave output routes stale. Define and test one lossless export/adapter codec: fill missing module versions from native descriptors, preserve existing settings/config/state/unknown fields, and validate/update output routes. Do not rename IDs or stamp arbitrary defaults over imported values. |
| Asynchronous refusal cannot use the existing synchronous catch path | UI graph/parameter setters are `void`; `App` currently catches immediate `EngineRefusal` to roll edits back. Network rejection arrives later. The protocol needs request IDs, acknowledgements, engine generation and an explicit asynchronous refusal/reconciliation path; document an additive `EngineClient` extension before implementation. `loadGraph` is already a Promise, but `App.loadPatch` currently starts it without awaiting/catching its result. Cover rejection, stale reply, disconnect and reconnect without losing the editable patch. |
| No existing browser control server | Audited `native/control`, `native/cli` and `native/io` contain app/CLI/audio/MIDI services, not a WebSocket/HTTP `EngineClient` endpoint. Reuse [app_engine.h](https://github.com/kalharbi11/wirescape/blob/6e3c253550428f2bb964af4434bd429b5284cce2/native/control/app_engine.h) and the Qt-free runtime loader, rather than routing through Qt UI methods. [engine2.h](https://github.com/kalharbi11/wirescape/blob/6e3c253550428f2bb964af4434bd429b5284cce2/native/engine2/engine2.h#L29) requires graph construction/configuration/state operations to be quiescent; edits and modulation-amount changes need controlled graph replacement or an approved control operation, never JSON work in the audio callback. |
| Telemetry is not yet the UI's telemetry | Native engine meters expose frame/generation/counter data; `output_sample` and processor state access are not a general cross-thread inspection API. UI needs effective values, phase, envelope position, held notes, event activity, per-module meters and scope buffers. Design a bounded render-owned snapshot/tap with non-realtime serialization, preserving visibility/throttling rules. UI `Ticker` accumulates sparse `effective` parameter deltas and clears that cache on graph replacement; `phase`, `envelope`, `meters`, `scope`, `eventActivity` and `heldNotes` are expected as current snapshots per packet unless the protocol and consumers are explicitly extended together. Output meters mean L/R; Mixer meters mean A/B. Send actual values; omit optional `outputs` if unavailable, and specify how unavailable required display fields appear. Never synthesize them inside `RealEngine`. |
| CC mapping is stored in the wrong layer for DSP | Browser labels save `ui.ccMap`. Native already accepts `midi.cc_to_cv` `config.rows` with controller/channel/smoothing fields via [runtime_module_config.h](https://github.com/kalharbi11/wirescape/blob/6e3c253550428f2bb964af4434bd429b5284cce2/native/document/runtime_module_config.h). Translate an explicit committed mapping to this configuration through an approved host operation; merely preserving `ui.ccMap` does not configure MIDI. |
| Preservation is different from execution | UI preserves and displays unknown modules/fields. Native runtime rejects unavailable/inactive modules, unknown v2 parameters, graphs above 64 modules/128 cables, documents over 2 MiB or excessive nesting. Keep the original editable document intact and surface a precise engine refusal. Do not delete unknown objects to make a graph load. |
| Device/status surfaces need real implementations | Existing CLI [play.cpp](https://github.com/kalharbi11/wirescape/blob/6e3c253550428f2bb964af4434bd429b5284cce2/native/cli/play.cpp) and [audio service](https://github.com/kalharbi11/wirescape/blob/6e3c253550428f2bb964af4434bd429b5284cce2/native/io/audio/DESIGN.md) provide lifecycle foundations, not all browser settings. Preserve optional capabilities: omit sample-rate/buffer/OSC setters when unsupported. Define CPU as measured audio callback load (recommended), specify latency measurement versus buffer-derived estimates, and report real dropouts/device changes. |

## Recommended first spike

1. Pin the native revision, establish the patch codec and protocol/refusal contract, and obtain the native project's required engine/threading review. Retain its realtime and device-confirmation rules.
2. Add a headless, loopback-only, token-protected host and `RealEngine.ts` behind explicit engine selection. A process-local token, strict permitted origin and bounded authenticated messages are engineering defaults; no LAN listener is needed. Keep FakeEngine as the deterministic browser-test backend.
3. Exercise **VCO → Output**, one cable and the VCO frequency knob. Round-trip a fully valid native v2 patch with explicit output routes. Use offline rendering/null devices in automation; a user runs the real-audio demonstration with the existing explicit confirmation mechanism.
4. Prove command acknowledgement/refusal, reconnect restoration, panic, status and one real output meter/scope snapshot. Add normalized-modulation parity fixtures before claiming the existing demo patch is interchangeable. Keep callback processing allocation-free; publish graph generations before retiring old graphs.
5. Expand to all `EngineClient` operations, polyphony and the done-checklist session. Packaging, kiosk launch, subtree import and Qt retirement follow a working host; they are not prerequisites for this spike.

## Decisions and owner work

Proceed with the plan's defaults: preserve IDs/unknown data, normalized modulation, sum-capable inputs, localhost-only transport, optional unavailable settings and dark theme deferred. Protocol acknowledgement shape, patch-codec ownership and render-safe telemetry are concrete implementation contracts to record and review; they do not need a new visual-design preference from the owner.

The owner must choose/confirm the actual output device for the first audible run. **Pi runner setup, runner registration and starting the private bridge remain the user's responsibility.** No agent should SSH to the Pi or open real audio/MIDI devices. OPEN-5 remains open until exact-revision Chromium FPS/frame-time evidence is produced on the Pi through the approved runner/user workflow; cloud measurements cannot close it. Confirm Pi resolution/input hardware when scheduling that validation (default 1920×1080 and mouse, with touch profile available).
