# F06 deterministic offline provider bridge proof

This is a bounded control-side proof against the existing native engine ABI. It has no discovery, MIDI/OSC transport, Qt, Python, audio device, device stream, or hardware path. The test drives `ws_engine_render` into a local sample buffer only. It does not establish live stability, real provider concurrency, or a public provider SDK.

## Ownership and clock

`ProviderBridge` has **one serialized control owner**. Only that owner calls `submit`, `flush`, `resume_after_quiescent_barrier`, and `ws_engine_enqueue` for its engine. The engine's SPSC enqueue mutates producer-owned fields and is **not** safe for several producers, even though the queue indices are atomic. A future provider worker must hand data to this owner through its own independently proven, bounded synchronized ingress. This proof has no such ingress and makes no MPSC or thread-safe submission claim.

Each input carries an unsigned monotonic nanosecond timestamp. A quiescently established `(epoch_ns, epoch_frame, integer sample_rate_hz)` anchor maps it to `epoch_frame + floor((timestamp_ns - epoch_ns) * sample_rate_hz / 1e9)`. The implementation splits whole seconds and fractional seconds so every multiplication and addition is checked without floating-point drift. Timestamps before the anchor and arithmetic overflow are refused. The configured rate must match the engine rate; this is a caller-established precondition, not an engine query. The fake-clock tests use 48 kHz and exact millisecond offsets. Clock drift, sync, rate changes, and transport handover remain outside this proof.

At submission, a timestamp beyond the engine's observed frame plus a finite future horizon is refused as backpressure for parameters and note-ons. A release (`WS_NOTE_OFF` or `WS_GATE`) that cannot be admitted instead stops and panics because this proof has no retry channel. The same rule applies to malformed or unconvertible releases. Pending storage is exactly 128 entries. Each `flush` examines at most `max_per_flush` pending entries, with a configured cap of 128. The engine itself retains its own bounded queue and render work limits. A stalled engine cannot cause unbounded bridge storage, though accepted future events can fill the engine queue and cause fail-closed panic.

## Event policy

The pending buffer is ordered by converted frame and stable arrival serial on ties. Only pending `WS_PARAMETER` values with the same node ID, parameter ID, and source ID are coalesced to the latest arrival. Note-on, note-off, and gate events are never merged; their source and note IDs pass through unchanged. A later parameter value can supersede an earlier pending value even if its timestamp is earlier. Once sent to the engine, an event cannot be retracted or coalesced.

Before enqueue, the bridge requires a frame at least the engine meter's current frame plus the configured maximum render block, covering a render call already in flight. It also requires nondecreasing frames relative to the last successful enqueue. A late/reordered parameter is clamped to this minimum and counted. A late/reordered note-on is rejected and counted. A late/reordered note-off or gate is treated as potentially lost voice ownership: the bridge stops forwarding, discards pending events, counts the loss, and calls `ws_engine_panic` once from the control owner. Pending overflow, engine `WS_CAPACITY`, and any other unexpected enqueue failure also stop and panic. An engine generation change observed before or after enqueue stops forwarding and drops the old epoch without a second panic.

Panic increments the public engine generation immediately, but its module voice reset applies at the **next active render boundary**. Generation equality or change does not acknowledge that reset. The bridge therefore never resumes automatically. The offline test explicitly quiesces both sides, performs an active `ws_engine_render` barrier into a local buffer, verifies old queue consumption, then calls `resume_after_quiescent_barrier` with a new clock epoch. The resume API relies on its documented caller precondition; it cannot prove consumer quiescence or reset application. A live adapter needs an explicit applied-generation acknowledgement or equally sound lifecycle barrier before it may reuse this pattern.

## Shutdown and limits

Shutdown order for a later host: stop acquisition; stop and join every worker that could produce ingress; stop and drain or discard ingress on its synchronization owner; stop the bridge control owner and prevent further `ws_engine_enqueue`; stop and join the render consumer; only then reset, rebuild, or destroy the engine and bridge. When a panic is pending, an active render barrier must occur before any claimed voice reconciliation. Inactive render does not apply panic reset. No producer or consumer may retain engine references after destruction.

The proof uses no allocations, locks, Qt, or Python in bridge submission or flushing. The bridge runs on the control side, not inside the render callback. `ws_engine_render` retains its existing overload behavior and may invalidate queued commands; a following generation observation stops this bridge. The bridge does not add an engine ABI type or modify the engine implementation. It does not guarantee that arbitrary outside producers obey ownership, that an externally triggered reset is applied, or that its fixed frame lead covers an unknown real device callback size.

## Acceptance

`native/tests/provider_bridge_tests.cpp` uses the actual Essentials modules in an offline engine. It checks stable frame ordering against a direct reference render, parameter coalescing, note/source identity, flush and storage bounds, future backpressure, late event policy, engine queue capacity panic, external generation fail-closed behavior, and explicit post-panic render-barrier rebase. Run it via the focused native CTest target once wired in `native/CMakeLists.txt`; no audio device should be opened.
